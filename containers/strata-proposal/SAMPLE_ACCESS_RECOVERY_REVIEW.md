## Reproduced conflict and fix

A native offline fixture now reproduces the observed signature: a complete JSON
sample is renamed into its visible name while a publisher DELETE-access handle
is still open. Python's ordinary read fails with **PermissionError, errno 13,
no Windows-specific error**. It reads normally after that handle closes. This
matches the latest attempt's sample-71 signature and later successful read.
The fixture establishes this concrete mechanism; it does not prove the handle
owner at the historical failure or assign a cause to the earlier generic fault.

The consumer now opens a completed sample through Windows CreateFileW with:

- Read-only access, OPEN_EXISTING and FILE_FLAG_OPEN_REPARSE_POINT.
- FILE_SHARE_READ plus FILE_SHARE_DELETE, **without FILE_SHARE_WRITE**.
- Exactly one data-open/read, a 4,096-byte frame ceiling and at most 4,097 bytes
  requested to detect overflow. No wait, retry, permission change or fallback.
- Plain disk-file/single-link checks on the opened handle, before/after size,
  identity and last-write checks, and a matching named-path identity after read.
  Reparse points, links, replacement, oversized or changing files are rejected.

This makes the completed rename compatible with the read. It does not permit
content writes or bypass access restrictions. Microsoft's
[CreateFileW sharing contract](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)
documents that delete sharing covers rename access and that incompatible open
handles still fail. Native tests confirm actual writer/exclusive conflicts still
fail immediately with Windows error 32. An injected access-denied error 5 is
propagated without a retry or permission change.

Frame parsing, sequence/provenance, live reader ownership, sample age and query
time checks remain in place. Rejected frames do not advance consumed sequence
or receipt time. Error reason and numeric OS/Windows codes are still saved after
stopping, with no arbitrary exception text. The fixed ASUS publisher script and
sensor source are unchanged; no new hardware readings were taken.

The first heartbeat byte is also published only after its temporary file is
complete. This closes an initial empty-file visibility gap without changing a
lease or accepting an empty heartbeat. Existing empty/regressed pulses still
fault. A failed earlier synthetic connected case remains preserved at
`.runtime/cache-verification-rehearsals/9d2aae9636d54657a4a135b665e3f060/`;
